# 第 10 章：9router 的配额追踪不是用户钱包

9router 很适合观察协议适配、连接选择与用量统计之间的关系。它的界面可以显示成本与上游配额，但不能因此假定具备用户充值余额、请求预扣和退款账本。阅读时必须从写入和准入路径证明这些能力。

## 10.1 上游额度用于连接选择

`open-sse/services/usage.js` 和各 provider 用量模块负责获取或解析配额信息。宿主选择连接时检查模型冷却和某些上游的已知额度状态。例如特定 provider 的剩余百分比为零且重置时间在未来时，可以跳过这条连接。[R](91-sources.md)

这些值的含义由上游定义，可能是窗口百分比、请求数或资源点，不能统一当成美元余额。仪表盘显示的零成本也不意味着基础订阅没有固定采购成本。

## 10.2 usage 如何进入数据库

流处理器收集内容和 usage，完成回调整理延迟与请求明细。`saveRequestUsage` 取得 SQLite adapter，通过统一价格计算函数求 cost，再在事务中写历史、日聚合和生命周期计数。按 provider、model、connection、API Key 和 endpoint 的聚合服务于查询与展示。

其中 pending 请求计数、最近记录环和统计通知有进程级 global 状态。数据库驱动按运行环境选择 Bun SQLite、better-sqlite3、Node SQLite 或 sql.js fallback。不能把某一驱动下的同步事务注释，扩大解释成所有驱动、共享文件和多副本都具有同样保证。

## 10.3 历史去重与扣费幂等不同

usage 历史写入会按时间、provider、模型、连接和 Key 等信息检查已有项，并更新聚合。这有助于减少同一次统计的重复记录，但不是一个以资金账户和不可变结算 ID 为核心的收费协议。

本书核对的普通聊天入口、usageRepo、定价与 Key 表结构中，没有看到与前两项目同等的“按用户钱包原子预扣、结束后差额结算”链路。这个结论限定于这些路径，不表示对全仓库所有插件和未来功能作不存在性证明。

## 10.4 文档示例不能替代可执行路径

配额说明可能包含预算告警、自动切换与示例费用。判断某项运营保证是否存在，应找到调用入口、存储字段、失败分支和验证方法，而不是只引用展示页面。成本示例还要独立验算：输入项与输出项之和必须等于总费用。

相同原则适用于 README 中的节省比例、模型数量和“不中断”等宣传措辞。本书不把这些数字当作测量证据。转发代码能运行，也不保证供应商合同、配额和价格永远不变。

## 10.5 若要增加商业计费

可以保留 9router 的 provider registry、转换器和流处理结构，在宿主层引入独立的预算与账务服务。这个服务必须知道付款主体、预留 ID、定价版本、用量证据和结算状态；不要让一个供图表使用的累计 cost 字段兼任钱包余额。

改动后还要重新核对转换和压缩对计量的影响。对供应商收费应使用实际发送内容和上游 usage 的合同，不能按压缩前的大请求估算值直接称为实际消费。

**练习：** 某请求历史显示 cost=$0.02。列出要证明用户实际被扣了 $0.02，还必须找到的账户更新、事务、去重、退款和日志证据。
