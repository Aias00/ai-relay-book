# 第 3 章：协议兼容不能只看文本是否出来

一个最简单的 user 消息几乎可以在任何两种聊天协议间转换。真正困难的是工具调用、推理块、缓存语义、图片引用、错误事件和终止原因。中转站若只通过“你好”测试，就可能在真实编程会话中破坏调用关系。

## 3.1 先固定四种名称

客户端模型别名、路由模型、上游实际模型、对外计费模型应当分别记录。例如 `coding-fast` 可以映射到某供应商模型，但用户购买的价格合同仍按 `coding-fast` 生效。只在最后把所有字段都覆盖成上游模型名，会失去解释价格和路由的能力。

new-api 在 `RelayInfo` 中区分原始模型和计费模型，并由价格辅助逻辑解析配置。sub2api 的计费输入还携带渠道映射信息和固定的定价时刻。9router 的模型服务与 combo 则负责解析 provider/model 和候选组合。[N][S][R] 的相关入口见[来源附录](91-sources.md)。

## 3.2 公共中间格式的收益与损失

9router 的转换器注册机制支持源格式到目标格式的直接路径，也支持通过 OpenAI 形状的中间表示。中间层减少适配组合数量，但只有能表达的语义才能保留下来。其 open-sse 说明专门指出 thinking、部分图片形式、工具 ID 和错误属性的转换损失风险。

因此，对于语义脆弱的协议组合，直接转换往往比两次转换更容易控制。代价是维护更多路径和测试。工程决策不是“统一格式一定更好”，而是列出每个字段在目标协议中的位置，并对无法表达的字段选择拒绝、明确降级或原样透传。

new-api 的独立 `relaykit` 模块把协议 DTO 和转换与宿主计费、认证、数据库拆开。这种边界有助于独立验证格式，但并不会自动证明每个 provider 的实现都符合最新合同。

## 3.3 缺失与零值不同

请求字段 `temperature` 未提供，与显式设置为 0 具有不同含义。把可选数字定义为普通标量并使用忽略零值的序列化规则，会让显式 0 在转发时消失。new-api 的请求约定使用可空指针表达可选标量，正是为了保留这项合同。

同样，usage 中缓存 Token 缺失、显式为 0、解析失败不能随意合并。缺失可能需要估算，0 是上游给出的值，解析失败则需要标记证据不可用。成本分析应保留用量来源，而不是把所有分支都写成精确整数。

## 3.4 工具调用需要完整生命周期

工具调用 ID 要能连接模型提出的调用与客户端回传的结果。流中参数可以分成多块，单个片段不是完整 JSON。若中转站在片段层执行 JSON 解析、改写名称或去掉错误标记，客户端可能无法继续下一轮。

建议按协议对建立固定样例：普通文本、空输出、工具参数分片、多个工具、拒绝、推理块、图片、usage 缺失、终态错误。比较的是结构和因果关系，不只是最终拼接文本。压缩工具结果等变换还要记录发生在转换前还是转换后；9router 的不同 provider 对此有特定顺序。

**练习：** 给一个包含显式 0、工具 ID 和缓存明细的请求/响应对，列出跨协议时需要保留、拒绝或降级的字段。一个成功 HTTP 状态为什么不能证明转换正确？
