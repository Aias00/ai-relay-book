# 第 17 章：完整业务域与模块边界

AI 网关首先是服务接入与供应平台。计费只是其中一组能力；把计费细分成很多模块，却把账号、调度和运行管理压在一个网关服务里，会得到失衡的架构。

## 17.1 按完整业务流程划分

下面是一种用于讨论职责的划分，不意味着需要部署 16 个微服务。

| 板块 | 业务域 | 主要职责 |
| --- | --- | --- |
| 客户接入 | 用户与租户 | 用户、组织、成员、租户隔离和生命周期 |
| 客户接入 | 身份与访问 | 登录、API Key、权限、访问范围和撤销 |
| 客户接入 | 开发者接入 | 文档、接入配置、Playground、调试 |
| 服务产品 | 模型与能力目录 | 别名、版本、参数、能力、上下架 |
| 服务产品 | 产品与商业规则 | 套餐、服务等级、售价、客户分组和权益 |
| 供应管理 | 供应商与渠道 | Endpoint、地区、代理、协议与能力映射 |
| 供应管理 | 账号与凭证 | 账号池、凭证刷新、失效、资源生命周期 |
| 供应管理 | 容量与健康 | 上游配额、并发容量、探测、冷却和恢复 |
| 请求运行 | 准入与治理 | 校验、限流、并发、排队、公平性与过载保护 |
| 请求运行 | 路由与调度 | 候选筛选、负载、黏性、重试和故障切换 |
| 请求运行 | 协议与执行 | 转换、网络调用、SSE、工具、多模态、取消 |
| 请求运行 | 任务与文件 | 提交、轮询、回调、恢复、结果交付和清理 |
| 平台经营 | 用量与计费 | 计量、计价、额度、账务、账单和调整 |
| 平台经营 | 订单与支付 | 购买、支付回调、续费、退款和对账 |
| 平台经营 | 运营与服务 | 通知、公告、工单、消费争议和经营分析 |
| 平台经营 | 安全与审计 | 滥用治理、数据保护、策略和风险调查 |

登录授权属于身份域，API Key 的消费上限属于额度规则；准入流程可以组合二者，但不应自己复制一套用户余额。管理后台是这些业务的入口，不是一个能够包办所有规则的业务域。

## 17.2 供应端也有完整生命周期

供应商接入后，要经过凭证验证、模型发现、容量配置、投入调度、健康反馈、冷却恢复和最终淘汰。渠道回答“如何连接、支持什么”，账号回答“以谁的身份执行”，容量回答“现在还能执行多少”。一个状态字段无法准确表达这三件事。

请求运行则围绕用户请求、上游尝试、用量记录和结算记录展开。一次请求可能经历多个上游尝试；一次成功响应不代表此前尝试没有成本。把所有信息压成一条最终日志，会失去解释重试和成本的能力。

文件与异步任务也需要独立生命周期：文件归属、上传、下载授权、结果有效期以及任务重启恢复，都不能仅靠普通 HTTP handler 的内存状态完成。

## 17.3 三个工程如何作为教材

根据本书固定版本的调用路径，sub2api 的 handler、service、repository 分层适合学习显式依赖与业务服务组织；new-api 的 relay、channel 与宿主业务协作适合学习丰富渠道接入；9router 的 provider、translator、executor 划分适合学习协议转换与执行分工。

这是不同学习目标的选择，不是完整项目质量排名。接口较多不等于业务域已经隔离，目录名叫 core 也不等于它可以脱离宿主运行。判断独立性应检查模块是否直接访问宿主数据库、共享全局配置、持有其他域的可变对象，以及是否具有可说明的失败契约。

## 17.4 公共技术底座

配置、密钥管理、数据库、缓存、消息队列、对象存储、HTTP 连接池、日志指标、插件运行时和部署系统是公共基础设施。它们支撑业务，不应反过来决定业务边界。例如，渠道健康是业务状态，Prometheus 指标只是其信息来源之一。

先建立模块化单体，明确状态所有者和接口，再根据扩缩容、权限与团队需求拆进程。不能把内部函数机械地替换成远程 RPC，然后期待系统自然获得更低延迟和更高可靠性。

## 17.5 练习

选一条渠道停用流程，分别标记管理入口、配置存储、调度状态、活动请求和审计记录。检查这些职责是否分散到多个层，以及哪个模块拥有最终解释权。
