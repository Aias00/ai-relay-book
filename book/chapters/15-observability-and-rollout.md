# 第 15 章：用指标和故障窗口控制上线

计费故障经常不会表现为请求错误：用户拿到了答案，账却没有扣；余额被扣了，日志却缺失；缓存显示可用，数据库已经透支。因此上线检查应把交付、资金和缓存分别观察。

## 15.1 延迟按阶段拆开

至少记录本地解析与估算、准入等待、Redis 预算操作、账户排队、上游首内容、总输出、结算入队、数据库提交与缓存收敛的耗时。关注 P50、P95 和 P99，而不是只比较平均值。

一次 Lua 的设计目标是减少预算热路径往返，不是保证整体首包只有一次 Redis 延迟。大请求 Token 计数、媒体读取、并发等待和上游首字节都可能更慢。没有同环境基准，不给三个工程编造性能排名。

## 15.2 能发现漏账的指标

| 指标 | 异常可能意味着什么 |
| --- | --- |
| 已完成请求但无结算命令 | usage 保存或任务提交存在缺口 |
| pending 命令数量与最老年龄 | worker 停止、吞吐不足或反复失败 |
| outbox 最老年龄 | 数据库已扣但缓存未收敛 |
| unknown 用量金额 | 断流、供应商证据不足或对账积压 |
| 预留总额与明细和的差 | 追加、释放或过期清理不一致 |
| 负余额用户数与负余额金额 | 风险政策是否被实际输出突破 |
| 单请求实际费用减预留 | 估算偏差、隐藏费用或定价漂移 |

只监控请求成功率会遗漏这些问题。告警应带请求或结算标识、账户范围和处理阶段，而不是输出完整提示词、上游凭据或可用的 API Key。

## 15.3 灰度分段预算

先在影子模式中计算目标预算和追加时机，但不影响上游输出，收集实际费用与估算误差。然后只对少量模型和用户启用，限制最大并发、输出和透支额度，观察预算拒绝是否误伤正常请求。

影子模式不能验证真正取消后的供应商费用。启用取消后还需要用真实账单检查停止延迟，对不能覆盖的隐藏推理和工具费用单独设置政策。策略升级时冻结单请求的定价和预算版本，避免长流中途被切换到另一套解释。

## 15.4 重启、备份与恢复

滚动发布应停止新准入，排空已有流和后台任务；期限到达后将未完成项标记为待恢复。进程退出钩子能改善正常关停，不覆盖断电或强杀，因此持久命令与数据库事务仍不可省略。

备份不只包括余额，还包括结算去重、未结束预留、outbox 和价格版本。如果恢复余额到昨天、去重记录保留今天，重放会被误认为已经扣过；反过来恢复去重而不恢复余额，也可能重复扣费。账务相关数据必须来自一致恢复点。

对于缓存重建，禁止直接用数据库余额覆盖活跃 Redis 账户而不协调事件位置。可以按账户进入恢复状态，让其他用户继续服务；恢复耗时应计入异常指标，而不是隐藏在无限重试里。

**练习：** 请求成功率 99.9%，但 pending 结算最老年龄持续增加。为何不应据此判定服务健康？列出你会暂缓的发布动作和仍可继续的只读功能。
