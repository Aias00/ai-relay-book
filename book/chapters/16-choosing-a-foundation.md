# 第 16 章：选择基础工程与实施顺序

选择基础项目，应看它已经拥有的状态和责任边界，而不是只看供应商数量或界面。本文的判断限定于固定版本源码，没有性能压测和生产事故统计支撑，不适合扩大成项目总体优劣排名。

## 16.1 按业务目标选择

| 目标 | 可以优先研究的基础 | 还要补的内容 |
| --- | --- | --- |
| 多供应商运营与丰富定价 | new-api | 普通钱包请求级恢复、输出预算和跨存储收敛 |
| 账户池与低延迟在途预算 | sub2api | 原子预算追加、持久化结算任务、过期与重建策略 |
| 个人或团队协议路由工具 | 9router | 若商业收费，另建资金账户与可靠计费服务 |

如果目标是“允许少量欠费，长流分段追加，优先减少延迟”，sub2api 的请求级 Redis 预留、续期、计费引用交接和最终数据库去重更接近所需结构。它仍不是成品：普通首笔准入、fail-open、scope 生命周期与队列可靠性都需重新决定。

## 16.2 已有系统不要为了一个模块整体迁移

已经使用 new-api 的平台，可以保留协议 adaptor、定价表达式、用户与日志体系，逐步引入请求级预算服务。迁移必须明确旧预扣和新预留不能同时对一笔请求生效，否则会双重占用甚至双重扣款。

给每笔请求冻结 billing mode 与版本，旧请求按旧规则结束，新请求按新规则开始。对照账务结果之后，再扩大范围。渠道和模型迁移不应顺便改变用户合同价格。

9router 则可以把预算当作宿主能力嵌入，而让 open-sse 继续负责格式和执行。成本统计服务可以消费结算事件，但不应反过来凭一个统计聚合值决定资金余额。

## 16.3 推荐实施顺序

第一步统一请求、尝试、预留、结算和事件身份，记录关联及金额单位。没有这一步，后续对账无法确定是不是同一笔。

第二步补持久化结算命令和数据库幂等，避免正常请求结束后因为 worker 退出漏扣。接着明确数据库到 Redis 的事件收敛和缓存重建协议。

第三步在准入加入受控输出预算与并发上限，统计误差和欠费。然后才增加流中追加预算，选择有代表性的文本模型灰度，并逐步处理隐藏推理、工具、图片和音频。

第四步演练提交前后崩溃、重复事件、缓存重建和长流取消，再决定是否需要更强的预留持久性。每一阶段都应能解释风险剩在哪里，而不是一次重写所有系统。

## 16.4 一个可验收的交付物

设计完成时，应能给出一份请求时序、一个账务状态表、一组存储约束、一张崩溃恢复矩阵，以及可复现实验结果。延迟目标写明测试环境和 P95/P99；风险目标写明并发、输出与透支政策；可靠性目标写明持久化边界和恢复时间。

新功能是否值得发布，不由“支持 Redis”“支持异步”或“有幂等键”这些单点能力决定。它取决于请求取得预算、消费产生、费用提交和异常恢复之间的证据是否连贯。允许少量欠费可以简化预算策略，但不能使丢失的账务事实变得可解释。
