# 第 20 章：多节点配置同步与渠道停用

推荐首次启动和恢复时使用全量快照，正常运行时使用增量事件；增量里携带单个资源的完整新配置。这里的全量快照只包含节点获授权的资源，不等于整个平台全部配置与密钥。

## 20.1 同步方式与版本

| 场景 | 方式 |
| --- | --- |
| 新节点启动 | 授权范围内全量快照 |
| 新增或修改渠道 | upsert 事件及该资源完整配置 |
| 停用或删除 | 明确状态变更或删除标记 |
| 短暂断线 | 从已处理位置补取增量 |
| 增量历史已清理 | 重新加载全量快照 |
| 周期校验 | 比较版本或摘要，发现差异后修复 |

资源完整替换比字段补丁更容易幂等，也避免遗漏字段删除。事件流位置用于恢复订阅，资源 revision 用于拒绝旧配置；可以按租户或订阅分区组织，不必让所有业务竞争一个全局序号。

快照必须绑定一致的流位置。例如快照对应位置 1000，后续从它之后补事件。先随意查询各表，再读取当前序号，可能遗漏查询期间发生的更新。实现上需要一致性快照与事件游标的协议。

## 20.2 新提供方的原子启用

新增提供方可能涉及渠道、凭证引用、模型映射、用户售价、成本和路由规则。先启用路由而价格或凭证未到，会产生不可执行或不可计价的请求。

可以按配置批次先暂存、校验依赖，再原子激活，也可以先创建禁用资源，依赖齐备后启用。若供应商需要新的签名算法或协议执行器，仅同步配置不够，还需要先部署能力并检查节点版本。

严格时间调价需要提前下发和确认，并处理未就绪节点。普通调价允许有限传播窗口时，应记录每个请求真正采用的版本，而不是假装所有节点在同一瞬间更新。

## 20.3 可靠发布停用事件

控制面在同一个数据库事务里更新渠道状态与版本，并写 outbox。发布器把事件交给可靠消息或 Watch 系统，失败重试。这样数据库提交后进程崩溃，不会让通知永久消失。

每个相关节点都必须获知变更。所有节点放在同一个竞争消费组，导致只有某个节点收到消息，不符合配置广播需求。可以使用各自游标的订阅，也可以由配置服务通过 Watch 推送并支持断线补取。

节点应用更高版本、更新可调度快照和相关缓存后，再确认版本。重复或较旧事件不能回退状态。后台应区分已提交、已传播、未确认节点和剩余活动请求。

## 20.4 排空与强制停止

排空停用阻止新调用，允许现有请求完成。强制停用还会查找渠道关联的活动请求并取消；异步任务是否调用供应商取消接口需要额外定义。取消网络连接不证明上游未产生费用。

请求可能已选中渠道，却尚未发送。节点应在执行准入边界再次协调停用状态，避免旧路由结果无条件放行。但一次额外读取仍有竞争窗口，需要定义哪个原子门控点代表调用已开始；越过该点的请求按在途请求处理。

## 20.5 分区时不能既无限继续又立即撤销

控制面断联时继续使用旧配置，就不能保证立即知道新的停用。配置租约可限制陈旧窗口：过期后停止新的调用。但租约不能追溯取消已经获准的请求。

普通维护可使用事件推送、版本门控、周期对账和有限租约。严格新调用授权可交给共享权威或受控出口，代价是增加同步依赖。泄露凭证还应在供应商侧撤销，清理本地缓存不能使攻击者持有的副本失效。

## 20.6 配置、用量与账务分别流动

配置从控制面到数据面，用量从数据面到结算端，余额由账务权威管理。可靠用量事件需要稳定标识、价格版本、用量来源与完整性；消费者幂等结算，不能因为配置广播机制可靠就推断扣款事件也可靠。

事件持久化前崩溃、上游已经执行但结果未收到等窗口仍需对账和恢复策略。异步交接不意味着所有费用事实都能自动找回。
