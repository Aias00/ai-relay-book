# 前言：从转发请求走向可解释的中转服务

把客户端的地址改成自己的域名，再把请求发给模型供应商，一个中转服务就能工作。但当两个用户同时消耗同一份预算、上游已经输出一半却断流、进程在扣款后退出时，能转发并不代表能把事情处理完整。

本书面向掌握 HTTP、JSON 和基本数据库操作的后端开发者，以 new-api、sub2api、9router 为三个源码样本。我们关心请求在哪里取得使用资格、模型和账户如何选择、协议转换丢失什么、何时产生费用，以及异常以后凭什么继续处理。书中涉及的上游接入均以运营者拥有合法使用权限和符合服务合同为前提，不提供绕过供应商限制的操作步骤。

## 阅读路线

第 1—6 章建立请求、路由、协议和流的共同语言。第 7—10 章分别拆解计价和三个项目的预算、统计实现。第 11—13 章提出一种允许少量欠费、优先降低首包延迟的设计，并解释它的并发和恢复边界。第 14 章运行独立的 SQLite 结算实验，第 15—16 章给出监控与选型方法。

如果你最关心收费，先读第 7、8、9 章，再读第 11—14 章。不要跳过第 5 章：计费设计必须承认流中收到的文本不等于供应商最终确认的用量。若你想做个人或小团队路由工具，可以从第 3、4、10 章理解 9router，再判断是否真的需要钱包和订阅账本。

## 三种证据分开阅读

本书的“当前实现”固定在 2026-10-27 核对的三个提交，完整提交号和文件入口见[来源附录](91-sources.md)。这些是本地无未提交修改的源码快照，提交存在于各自上游 GitHub 仓库；不是对未来版本的承诺，也没有用源码阅读代替真实上游测试。

第 11—13 章的预算模型是待实现的设计，不是三个项目已经拥有的功能。第 14 章和代码附录则属于本书自己的教学实验：真实 SQLite 文件、独立进程、事务和重复投递；没有真实 Redis、SSE、支付渠道或供应商调用。测试结果只能证明实验中对应的断言。

所有金额例子都是用于算账的假设价格，不是模型报价。为避免小数误差，实验使用整数微美元，一美元等于一百万微美元；这与 new-api 默认一美元对应五十万 Quota 的单位不同。不同章节的单位不能直接混用。

## 书中最重要的区分

预扣是先改变余额，再按实际费用补退；预留是先占用可用额度，结算时才改变余额；用量统计则可能只记录发生了什么，根本没有资金账户。三者都可能显示一个 cost 字段，但不能因此视为同一种账务系统。

同样，一次 Redis Lua 可以原子地完成局部判断，却不能让 Redis 与 SQL 数据库自动组成事务。一个唯一键可以防止重复扣款，却不能找回尚未持久化的计费任务。读懂这些边界，比给项目贴上“高性能”或“不可靠”的标签更有用。
