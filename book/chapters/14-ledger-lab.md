# 第 14 章：运行一个可崩溃的结算实验

本章验证第 13 章数据库部分的核心主张：持久命令不因 worker 退出消失，两个进程不能覆盖彼此扣款，同一命令不能重复收费，结算与 outbox 必须一起提交。实验独立于三个被研究的工程，只使用 Python 标准库和真实 SQLite 文件。

## 14.1 运行与预期

从本书仓库根目录执行：

```sh
python3 -m unittest discover -s tests -v
python3 -m lab.ledger demo --db /tmp/relay-ledger-demo.sqlite
python3 -m lab.ledger inspect --db /tmp/relay-ledger-demo.sqlite
```

demo 要求一个尚不存在的路径，避免覆盖之前的实验。金额单位是微美元。初始余额 10000000，保存一条消费 1500000 的命令，结算两次后仍应是 8500000。结果中有一条结算和一条 pending outbox，后者的 delta 为 -1500000。

代码在下载区实验 ZIP 和书末自动生成的代码附录中。无需真实模型账号、Redis 或网络连接。测试采用两个独立进程和 barrier 协调起跑，不使用计时快慢来判断账务正确性。

## 14.2 四张表的责任

| 表 | 保存什么 | 保证什么 |
| --- | --- | --- |
| accounts | 用户整数余额 | 原子增减的目标 |
| commands | 用户、请求 ID、实际金额 | worker 开始之前命令已经持久化 |
| settlements | 已应用的请求与金额 | 同一用户请求只能认领一次 |
| outbox | 余额增量和待投递状态 | SQL 已提交后仍能找到缓存更新工作 |

这里的实际金额直接作为命令输入，省略定价和 usage 解析。生产系统还需保存价格版本、用量证据、预留身份和退款关系。实验没有实现任何预算准入，因此可以记录负余额，但不证明欠费风险受到控制。

## 14.3 两个进程更新同一个账户

测试为请求 A 保存 3000000、B 保存 4000000 的命令，再启动两个进程。两个进程各自打开数据库连接，执行 BEGIN IMMEDIATE、认领、余额减款、outbox 插入与提交。最终余额必须是 3000000，两个结算和两个事件。

SQLite 在这里通过写事务串行化保证冲突处理。断言验证没有丢失扣款，不是吞吐测试，也不能把 SQLite 的单写者行为直接迁移成 PostgreSQL 或 MySQL 的锁方案。

另一条测试让两个进程同时处理 A。唯一键使其中一个已经应用后，另一个返回未新增；最终仍只扣 1500000。相同请求 ID 如果携带不同金额，入队阶段会明确拒绝，不能把冲突视为普通重复消息。

## 14.4 提交前退出

crash hook 在 UPDATE 之后、事务提交之前调用 `os._exit(71)`。这绕过 Python 正常清理，模拟 worker 突然消失。重新连接后余额仍为 10000000、结算为 0，先前单独保存的命令仍在 pending 列表中。

重放这条命令后余额变为 8500000。这里恢复的关键不是捕获异常，而是未提交事务不能成为最终账务事实，已保存命令可以再次执行。

## 14.5 提交后退出

另一条 hook 在 COMMIT 之后、返回成功之前调用 `os._exit(72)`。此时余额已经是 8500000，结算和 outbox 都存在。再次初始化不会重置余额，重放命令也不会再次扣费。

缓存更新事件仍为 pending，说明可以由接管者继续投递。实验没有缓存消费者，因此不会宣称 Redis 已更新，也没有用一个假的内存缓存来冒充跨系统恢复测试。

## 14.6 下一步怎样扩展

接入真实 Redis 后，应新增“事件已执行、确认未提交”的重复投递测试，以及缓存清空后按快照和事件位置重建的测试。接入真正 SSE 后，应新增追加预算失败、客户端断开、上游继续执行、最终 usage 缺失等协议测试。

每加一层，只扩展相应证据。六条数据库测试全绿，仍不等于供应商成本准确、取消立即生效或多地区部署安全。
