# 第 11 章：允许少量欠费时，怎样缩短准入路径

如果业务允许有限透支，就不一定需要每笔都冻结最大可能费用。但应明确接受的是估算和取消延迟造成的小额差异，而不是计费任务丢失。下面是一个建议设计，不是三个项目已有实现，也没有未经测量的性能承诺。

## 11.1 先写风险政策

定义账户允许透支额度 L、最大并发 N、输出硬上限、最大请求时长以及未知费用处理期限。准入时可以使用：

```text
可用预算 = 已结算余额 B + 允许透支 L - 在途占用 H
允许新请求 ⇔ 可用预算 ≥ 本次申请预算
```

L 不是最终负余额的绝对上限。仍在运行的请求可能产生超出预留的费用；如果没有并发和输出限制，“少量欠费”就只是愿望。第 12 章用分段补充预算降低这个差额。

## 11.2 一次 Lua 内完成读取和占用

让 Redis 保存已结算余额缓存、预留总额、每笔预留及其版本。请求本地完成估算后，一次 Lua 读取余额和预留总额，检查余量，再登记请求。应用无需先 GET 余额再调用扣款脚本。

但“一次 Redis 往返”只描述缓存已准备好的预算热路径，不包含认证、并发排队或其他路由操作。当前 new-api 和 sub2api 都有前置检查，不能直接声称它们已经只有一次 Redis 操作。

同一账户下的余额、Key 占用和请求明细若要一次 Lua 修改，在 Redis Cluster 中必须设计同槽 key。跨用户共享的上游账户额度不能随意塞进同一个用户槽；它应作为独立调度资源，避免为了省一次往返破坏分片边界。

## 11.3 不要每次扫描所有预留

sub2api 当前钱包脚本通过 HASH 求和。改进设计可维护 `reserved_total`，新增、追加、完成时按差额更新。过期清理应分批执行并同步扣减总额，而不是用 HVALS 每次遍历全部成员。

这个优化把复杂性转移到一致性：请求重复释放不能再次减总额，清理与追加不能交错复活旧版本。需要请求状态、操作序号和条件更新，而不是单独加一个计数器。

## 11.4 估算也可能比 Redis 更慢

精确 Token 计数、大请求解析和媒体下载可能进入首包路径。应本地缓存定价，将媒体的预算依据限定为已经取得的数量、尺寸、时长和受控上限。不要为了一次预算估算在热路径额外下载远程图片或探测大音频。

粗估可以提高速度，但必须有数量上限和后续实际结算。隐式推理、搜索和工具费用需要独立预算项；只按可见输出字数估算会遗漏这些费用。

## 11.5 缓存缺失需要专门协议

Redis 没有账户余额时，从数据库加载并不总是安全：数据库可能已经包含某笔结算，而旧事件稍后又来更新 Redis，造成重复减款。反过来，数据库余额也可能尚未包含只在缓存中的变动。

因此初始化应协调账户版本、未结束预留和事件位置。恢复期间允许暂停该账户准入，或者使用明确有风险上限的降级。不能由多个进程各自读取数据库，然后无条件 SET 覆盖别人刚更新的余额。

**练习：** 数据库余额 8.5 已包含事件 E，Redis 丢失后重新加载 8.5，随后 E 被重放。为什么单纯的 `balance -= 1.5` 会出错？给出事件位置或重建版本的解决思路。
