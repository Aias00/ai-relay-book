# 第 2 章：沿三个工程追踪一次请求

源码阅读从“一个请求在哪里结束”倒推往往更有效。入口文件告诉你路由，响应处理器告诉你何时已经向客户端提交内容，计费调用告诉你费用在哪个线程或任务中发生。只看目录名称容易把异步统计误认为同步结算。

## 2.1 new-api 的请求链

在固定版本 [N](91-sources.md) 中，`controller/relay.go` 的 `Relay` 建立请求上下文，调用 `relay.PrepareRequestBilling`，然后进入渠道尝试循环。重试时会重新选取渠道，并通过 `PrepareTieredBillingForSelectedGroup` 调整分组相关预算。请求体由可复用的存储提供，不是简单重复读取已经消耗完的网络流。

以兼容聊天路径为例，`relay/compatible_handler.go` 调用 adaptor 发送请求，再执行 `DoResponse`。后者可能已经转发 JSON 或完成 SSE 处理；随后调用文本或音频消费结算。因此“当前 handler 同步结算”与“客户端尚未看到响应”不是同一回事。

本次计费对象挂在 `RelayInfo.Billing`，表达式快照挂在 `TieredBillingSnapshot`。失败后的公共处理会尝试退还预扣，并处理适用的违规收费政策。是否重试、是否收费、是否降低渠道健康度，是三个需要分别检查的决定。

## 2.2 sub2api 的请求链

在 [S](91-sources.md) 的 `backend/internal/handler/gateway_handler.go` 中，可以看到先获取用户并发槽位，等待结束后再次检查余额或订阅资格，再调用在途预留。等待后重查有实际意义：排队前看到的余额，可能在等待期间已被其他请求消耗。

handler 还会生成用于账户调度的粘性信息，进入账户选择与转发。响应结果被整理为 `RecordUsageInput`，携带用量、用户、Key、账户、定价时刻和必要的上下文快照。后续 worker 使用这些值处理实际扣费，不应继续持有整个大请求体。

默认组装中的用量 worker 是进程内有界执行器。没有注入 worker 或 worker 已停止时，普通提交路径会回退到同步执行；特定 overflow 策略仍可丢弃普通任务，强制计费提交路径有额外兜底。因此不能把“有 worker”概括成“所有计费都可靠异步”。

## 2.3 9router 的请求链

在 [R](91-sources.md) 中，`src/app/api/v1/chat/completions/route.js` 初始化转换器并调用 `src/sse/handlers/chat.js`。宿主层处理模型解析、combo 和可用连接，`open-sse/handlers/chatCore.js` 负责转换、请求变换、执行器调用以及响应处理。

open-sse 将 provider 特殊逻辑放到执行器或对应处理模块。`chatCore/streamingHandler.js` 建立转换流和断开处理，将响应交给客户端。用量则进入 `src/lib/db/repos/usageRepo.js` 的历史和统计数据。请求转发成功与统计写入成功要分别观察。

## 2.4 把一条路径画成责任表

| 阶段 | 要保存或判断的事实 | 不应推断的事实 |
| --- | --- | --- |
| 准入 | 身份、预算、并发资格 | 上游一定会接受 |
| 选择 | 模型、账户、定价版本 | 能力一定完整兼容 |
| 发送 | 尝试 ID、发送时刻 | 超时代表未执行 |
| 响应 | 首字节、内容、终态、usage | 收到文本代表完整成功 |
| 结算 | 实际金额、依据、去重结果 | 日志写入等于资金已提交 |

读其他模态时重新走一遍这张表。视频任务、WebSocket、多轮工具调用可能拥有不同生命周期，不应强行套进“一次 HTTP 返回就结束”的模型。

**练习：** 在一个处理器里标出最后一次写响应的位置、实际计费的位置、进程内异步提交的位置。解释为何客户已经收到最后一个字时，数据库仍可能没有完成扣款。
