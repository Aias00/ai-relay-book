# 第 8 章：new-api 的预扣、订阅记录与差额结算

new-api 的普通钱包路径先扣一笔估算额度，响应处理后按实际费用补扣或退差额。请求级状态由 `BillingSession` 维护；账户余额与这份状态的存储位置不同。这个区别决定了进程异常退出后可以恢复什么。

## 8.1 预扣如何估算

`PrepareRequestBilling` 先调用 `EstimateRequestToken`。开启请求计数时，文本经过本地 Token 计数和结构开销估算，媒体可能进入专门读取或估算路径；关闭计数时输入估算为 0。

普通表达式预扣把 `P` 和 `Len` 设为估算输入，`C` 设为 0，再换算 Quota 并乘分组倍率。Token 计价分支还乘 `pre_consume_multiplier`，默认 1；固定请求价格分支不乘这个预扣倍率。旧 Token 倍率路径也是估算输入乘相关倍率，不按客户端最大输出数预扣完整输出预算。[N](91-sources.md)

钱包还可能走信任额度旁路：默认门槛为十美元，钱包以及受限 Key 要满足门槛，钱包仍需覆盖估算预留。订阅与强制预扣任务不使用这条旁路。具体是否生效取决于部署配置。

## 8.2 同时调整资金与 Key 限额

`BillingSession.preConsume` 先预扣令牌额度，再预扣资金来源；后一步失败会尝试回滚前一步。钱包以 `UserId` 识别，Key 以 `TokenId` 识别，缓存操作还使用 Key 派生的缓存键。订阅以用户实际购买的 `UserSubscriptionId` 识别，而不是产品计划 ID。

钱包 `TryReserveUserQuota` 在 Redis 可用且命中时用 Lua 检查与扣减；没有 Redis 或缓存路径失败时使用数据库 `WHERE quota >= amount` 条件更新。Redis 成功后，增量直接落库或进入批量更新。没有 Redis 的钱包原子预扣直接走数据库，并非先放入进程内批量队列。

前置余额读取与原子预扣是两步。`GetUserQuota(id, false)` 在开启 Redis 时读取缓存；真正抵御并发抢余额的是预扣时的条件更新。前置读取成功不代表后一步一定成功。

## 8.3 钱包请求记录没有随余额一起持久化

内存中的 `BillingSession` 保存 `preConsumedQuota`、`tokenConsumed`、`extraReserved`、资金来源及 settled/refunded 标记。钱包预扣只更新余额，没有单独按 `RequestId` 写一条钱包预扣流水。

因此，Redis 能知道用户被扣后的余额，却不能仅凭余额知道请求 A 扣了 100、请求 B 扣了 200。开启批量落库时，待写增量保存在按账户聚合的进程内 map 中，这也不是可恢复的请求账本。

进程在预扣后退出，可能留下已经扣减的余额而丢失请求会话；进程内互斥锁能防止当前对象的重复调用，不能让另一个进程重建这次未完成结算。

## 8.4 订阅的请求记录多了一层

`SubscriptionPreConsumeRecord` 在数据库保存以下字段：

| 字段 | 用途 |
| --- | --- |
| `RequestId` | 唯一索引，定位请求预扣 |
| `UserId`、`UserSubscriptionId` | 定位用户和具体订阅 |
| `PreConsumed` | 初始预扣 Quota |
| `Status` | consumed 或 refunded |
| `Id`、`CreatedAt`、`UpdatedAt` | 主键与时间信息 |

初始预扣记录与订阅 `AmountUsed` 增加在同一事务中提交。但正常差额结算不把记录改成最终金额，也没有 settled 状态。发送前追加的订阅预留还在会话里另记 `extraReserved`，不能只读初始记录就当成全部占用。

退款按请求 ID 读取记录并检查 refunded 状态。不过固定版本的退款函数在外层事务内调用 `PostConsumeUserSubscriptionDelta`，后者另开数据库事务，而不是复用传入的 tx。因此不能仅凭函数注释宣称“额度退回与退款标记”已经是同一个原子提交；实际故障窗口应由数据库实测确认。

## 8.5 同步计算不代表同步落库

普通兼容聊天路径在响应处理后直接调用 `PostTextConsumeQuota` 和 `SettleBilling`，差额为实际费用减已预扣额度。钱包差额可经批量落库，部分缓存更新异步执行；失败预扣退款也通过 goroutine 池执行。异步任务则在任务完成后重新计算，具有另存的任务计费上下文。

钱包最终补扣允许余额降为负数。订阅差额更新则检查总额度，超限可以返回错误；不能把钱包负余额的行为泛化到订阅。结算失败应作为账务异常处理，而非只看响应已经成功就忽略。

**练习：** 预扣 1000、追加 500、实际消费 1200，分别列出钱包会话、订阅初始记录和最终差额。在哪个位置杀死进程会丢失仅存内存的事实？
