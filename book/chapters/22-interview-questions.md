## 1 AI 网关和普通反向代理有什么区别

**参考答案**

两者都处理网络转发，AI 网关还需要理解调用的业务语义。它要识别模型能力、选择供应商和账号、转换请求及响应协议、处理工具调用和多模态内容，并采集用量。长时间流式输出还要求正确处理客户端断开、上游超时、取消和部分失败。

架构上可以分为管理面与请求执行面。管理面负责用户、模型、渠道、凭证和策略的生命周期；请求执行面根据配置快照完成鉴权、准入、路由和转发。二者可以部署在同一个进程，但不应让每个请求重复查询所有管理配置。

一次用户请求可能对应多次上游尝试，需要分别记录请求级结果和尝试级结果，才能解释重试、总延迟、上游错误和成本。

**追问：是否应该一开始就拆成微服务？**

不必。先做职责明确的模块化单体，通常更容易控制调用开销和故障处理。是否拆服务，应看独立扩缩容、团队边界和故障隔离需求。协议转换、计价等纯计算能力可以先作为进程内模块；拆成远程服务会引入网络延迟和新的可用性依赖。

**源码阅读**

- new-api：`router/`、`middleware/`、`relay/`、`controller/`、`service/`。
- sub2api：`backend/internal/handler/`、`service/`、`repository/`。
- 9router：`src/sse/handlers/chat.js`、`open-sse/handlers/chatCore.js`。

阅读任务：画出一次请求的调用链，标记外部等待、状态修改和失败退出位置。

## 2 API Key 撤销后如何让多实例及时失效

**参考答案**

需要先定义撤销时效。每次请求都查权威存储，可以缩短陈旧窗口，但增加延迟与存储压力；使用本地缓存则必须处理失效传播。

常见方案是持久化撤销状态，更新共享缓存，再通知各实例清理本地缓存，同时设置较短 TTL 作为漏通知后的兜底。缓存值也可以带权限版本，帮助识别旧状态。失效与并发回填需要配合处理，避免一个旧查询在失效后重新写入缓存。

仅依赖 Redis Pub/Sub 不能保证离线实例收到通知。严格撤销场景需要更强的权威检查、可恢复事件或短期凭证，并明确缓存故障时的策略。

撤销一般影响后续请求，已经建立的流是否立即中止是另一项产品规则，需要维护活动请求与身份之间的关联。

**追问：如何避免 API Key 校验泄露密钥？**

客户端提供的 Key 不应写入日志。可以存储不可直接用于调用的校验摘要，用非敏感标识做查询、审计和展示。客户端访问凭证与上游凭证要分开处理：上游调用需要原始凭证，应通过受控密钥存储和加密保护，而不是把所有凭证都当成同一种可哈希数据。

**源码阅读**

- new-api：`middleware/` 与 token 相关模型。
- sub2api：`backend/internal/service/api_key_service.go`、`api_key_auth_cache_impl.go`。

阅读任务：追踪撤销路径是否覆盖数据库、共享缓存和本地缓存，并检查进程错过通知后的行为。

## 3 同名模型能否直接切换供应商

**参考答案**

不能仅凭名称判断。相同对外名称可能对应不同模型版本、上下文长度、工具能力、图片输入、结构化输出、缓存语义或服务等级。

模型目录应区分对外模型名、内部能力描述和上游实际模型标识。路由先筛选满足请求能力的候选，再比较健康、成本和负载。不能为了切换成功而静默丢弃必要参数，否则接口虽然返回成功，语义已经变化。

可以把能力分成必须满足和允许降级两类。是否允许降级应由接口约定或用户选择决定，并且能够在日志中解释实际路由结果。

**追问：统一模型别名的价值是什么？**

它可以降低调用方与供应商具体名称的耦合，也方便迁移和灰度。但别名需要可追踪的映射版本，保留实际模型和渠道信息。供应商切换不代表输出质量、行为或价格完全相同。

**源码阅读**

- new-api：`relay/helper/` 中模型映射相关逻辑。
- 9router：`open-sse/providers/capabilities.js`、`open-sse/config/providerModels.js`。

阅读任务：寻找能力不匹配时是拒绝、转换还是删除参数。

## 4 多实例同时刷新一个上游凭证怎么办

**参考答案**

并发刷新可能浪费请求，也可能在 refresh token 轮换时让后完成的旧结果覆盖新凭证。单进程可以用 singleflight 合并刷新，多实例还需要共享协调机制。

一种方案是按上游账号获取带过期时间的刷新锁，获得锁后再次检查凭证是否已经被其他实例刷新。刷新成功时，用版本条件更新持久化凭证，再通知缓存失效；等待方重新读取结果。

只加锁还不够。执行者可能暂停到锁过期后继续运行，所以写入时仍需版本比较或其他防止过期执行者覆盖的机制。释放锁也必须校验锁的持有者。

**追问：刷新成功，但新凭证还没保存进程就崩溃了怎么办？**

这是外部供应商操作与本地存储之间的故障窗口，本地事务无法覆盖。恢复方式依赖供应商是否允许旧 refresh token 重用、是否有轮换宽限期或查询恢复接口。应缩短窗口、记录刷新状态并设置重新授权路径，不能承诺一个分布式锁就能消除这种风险。

**源码阅读**

- sub2api：`backend/internal/service/` 中 token provider 与 token refresher。
- 9router：`open-sse/services/tokenRefresh/`、`oauthCredentialManager.js`。

阅读任务：区分进程内合并、跨实例互斥、数据库版本更新三种不同保证。

## 5 为什么有 QPS 限流还需要并发限制

**参考答案**

QPS 控制进入速度，并发限制控制正在占用资源的请求数量。AI 请求耗时长且波动大，即使进入速度不变，上游变慢也会使在途请求积累。

稳定系统中，平均在途数量约等于平均到达率乘以平均停留时间。例如每秒 100 个请求、平均持续 30 秒，平均在途数量约为 3000。容量还必须考虑长尾耗时、突发和重试。

可以分别设置用户公平性限制、上游账号容量限制和实例保护限制。排队也需要长度及等待时间上限，否则只是把拒绝变成更长的等待。

**追问：流式请求什么时候释放并发槽位？**

应该在请求真正结束或资源清理完成时释放，不能收到上游响应头就释放。成功、失败、超时和取消都要覆盖，且只能释放一次。多实例共享计数还需要租约或异常恢复，避免实例崩溃后永久占用。

**源码阅读**

- sub2api：`backend/internal/service/` 中 concurrency、rate limit 与 session limit 相关实现。
- new-api：`middleware/` 中限流逻辑。

阅读任务：检查异常退出和客户端断开是否释放占用。

## 6 上游返回 429 应该换账号还是换供应商

**参考答案**

先判断限制的范围。429 可能表示账号 RPM、token 配额、供应商共享项目额度或区域容量不足。账号级限制可以尝试其他独立账号；共享项目额度耗尽时，换同项目账号可能没有意义；供应商整体拥塞时，可以选择其他满足能力的渠道。

应结合响应头、错误体、近期错误分布和资源关系判断，并设置冷却时间。尊重有效的 Retry-After，同时限制重试次数和总耗时，避免重试放大上游压力。

429 通常应作为临时不可调度反馈，不能一律永久封禁账号，也不能无限切换。

**追问：熔断和重试有什么区别？**

重试针对当前请求再次尝试，熔断针对一段时间内的资源选择。熔断器通过失败统计暂停向异常资源发送普通请求，再用有限探测判断是否恢复。统计范围需要匹配故障范围，不能因为一个模型不可用就让整个供应商永久退出。

**源码阅读**

- sub2api：`backend/internal/service/openai_account_scheduler.go`。
- 9router：`open-sse/services/accountFallback.js`、`combo.js`。
- new-api：`service/channel_select.go`。

阅读任务：看错误分类如何影响账号、模型和渠道的后续选择。

## 7 统一协议为什么可能造成信息丢失

**参考答案**

不同协议的语义不完全一致，包括内容块、工具调用标识、工具错误、推理内容、多模态引用和终止原因。统一到一个中间格式时，如果中间格式没有对应字段，第一次转换就可能丢失信息，后续无法恢复。

设计上可以保留原始字段或扩展字段，为敏感协议对提供直接转换，并明确声明不支持的能力。同协议透传也需要遵守访问和请求策略，不能绕过必要校验。

转换正确性不能只检查 JSON 能否解析，还需要验证多轮工具调用、流式增量和显式零值等语义。

**追问：为什么可选参数需要区分未提供和零值？**

未提供通常表示使用默认行为，显式的 0 或 false 可能是用户有意关闭某项能力。Go 请求结构体若使用非指针标量配合 omitempty，可能在重编码时丢掉这些显式值。应使用能够表达是否存在的字段类型，并测试往返转换。

**源码阅读**

- 9router：`open-sse/translator/index.js`、`request/`、`response/`。
- new-api：`relaykit/` 的 DTO 与协议转换。

阅读任务：比较直接转换与通过中间协议转换时，哪些字段不能保真。

## 8 SSE 已经输出一半还能重试吗

**参考答案**

通常不能把第二次生成直接拼接到第一次输出后面。新生成可能重复内容、改变上下文，工具调用 ID 也可能冲突。HTTP 响应开始后，通常也不能再改成另一个 HTTP 错误状态。

应区分尚未向客户端输出和已经输出两个阶段。前者仍需判断上游是否可能执行以及操作是否可重试；后者通常通过协议允许的错误事件或连接终止表达失败。真正的续传需要上游协议支持恢复标识、序号和一致的会话语义。

超时也应细分为连接超时、首响应或首有效内容超时、流空闲超时和总截止时间，避免用一个短超时误杀正常长输出。

**追问：一个网络 chunk 是否对应一个 token？**

不是。网络读取块、SSE 事件和模型 token 是三个层次。一块数据可能包含多个事件，也可能只有半个事件。内容事件可能包含多个 token，其他事件则只携带状态或 usage。需要增量解码并按事件边界解析，不能按 chunk 数计量。

**源码阅读**

- 9router：`open-sse/handlers/chatCore/streamingHandler.js`、`open-sse/utils/streamHandler.js`。
- new-api：`relay/channel/` 中流式响应处理。

阅读任务：检查半帧、正常结束、上游断连和客户端取消四条路径。

## 9 一万个流式连接需要一万个线程吗

**参考答案**

不需要。Go 把大量 goroutine 调度到较少的操作系统线程上；网络等待通常由网络轮询机制处理，不要求一个连接长期占用一个线程。

但连接仍消耗文件描述符、socket 缓冲、TLS 状态、goroutine 栈和应用缓冲。一万个客户端连接可能还对应大量上游连接，因此不能只统计入口连接数。

CPU 核数主要影响同时执行的计算工作。网关如果卡在数据库、网络、内存或上游容量，增加核数不一定有效。应结合 CPU、堆内存、goroutine、连接池等待和网络指标定位。

**追问：客户端读得很慢会怎样？**

会形成背压。如果网关持续读取上游并无限缓存，内存可能不断增长。应使用有界缓冲和取消传播，必要时设置写入期限或慢客户端策略。停止本地读取不保证上游立即停止生成，取消后的成本处理仍要有规则。

**源码阅读**

- new-api：`service/http_client.go`、`service/http_transport_policy.go`。
- sub2api：上游 HTTP 客户端、响应转发与取消路径。

阅读任务：找到每个请求启动的 goroutine，确认谁负责退出以及何时释放连接。

## 10 视频任务完成回调重复发送怎么办

**参考答案**

回调应该按至少一次交付来处理。先验证来源和任务归属，再根据上游事件 ID、任务 ID 与状态版本进行去重，通过条件更新控制状态转换。

任务状态机应禁止终态被普通旧事件回退。重复的成功通知不能重复生成资产、通知用户或扣费。状态更新与可靠后续事件可以在本地事务中通过 outbox 关联，消费者再幂等执行后续动作。

回调处理应尽快确认，耗时工作放入可靠队列。轮询可以补偿漏回调，但两条路径必须进入同一状态转换规则。

**追问：提交上游成功，但保存上游任务 ID 前崩溃怎么办？**

如果上游支持幂等键或按客户端关联 ID 查询，应先持久化本地提交记录，用稳定标识提交，再恢复关联。如果上游没有相关能力，就存在无法完全自动判定的窗口，需要对账或人工处理，盲目重试可能创建第二个收费任务。

**源码阅读**

- new-api：`service/task_polling.go`、`relay/relay_task.go`。
- sub2api：`backend/internal/service/batch_image_worker.go` 及任务恢复逻辑。

阅读任务：查看重启后任务从何恢复，以及终态处理是否能够重复执行。

## 11 上游没有返回 usage 应该怎么处理

**参考答案**

先区分用量不存在、尚未到达和传输丢失。部分流式接口在最后一个事件提供用量，客户端提前断开可能导致网关没有拿到完整统计。

计量优先使用经过校验的上游用量，再考虑任务查询或账单补取；只能估算时，应标注来源、算法版本和完整性。文本 tokenizer 可以估算可见文本，但通常无法精确还原隐藏推理、供应商缓存和某些多模态计量。

还应统一缓存等字段的口径：有的供应商输入总量包含缓存命中，有的分开报告，不能简单把所有字段相加。用量事实与价格规则要分开保存，方便核对和重算。

**追问：请求执行期间修改价格应该按哪个价格收费？**

由产品约定决定，常见做法是请求准入时冻结价格快照，最终用实际用量按同一快照计价。快照需要覆盖价格版本、折扣、币种、舍入规则和参与计价的条件。仅保存表达式字符串而重新读取当前时间或当前分组，未必能重现原费用。

**源码阅读**

- new-api：`service/token_counter.go`、`service/tiered_settle.go`、`pkg/billingexpr/`。
- sub2api：`backend/internal/service/billing_service.go`。

阅读任务：分清估算、实际用量归一化、计价以及余额修改的入口。

## 12 消费成功但扣费失败怎么恢复

**参考答案**

执行结果与财务结算需要分别记录。请求成功后产生带稳定结算标识的用量或结算事件，持久化交接给后续处理。消费者在一个数据库事务中完成幂等校验、账务变动和结算状态更新，失败后可以重试。

幂等标识要对应一项业务扣款，不能简单把所有上游尝试都视为用户扣费。相同标识重复提交时还应比较关键内容，防止不同金额被错误当作相同操作吞掉。

如果数据库已经提交而确认消息丢失，重试通过幂等记录识别已经完成。长期失败的事件进入可追踪的异常处理流程，并通过用量、账单和账户流水对账。

**追问：放进 goroutine 异步扣款就够了吗？**

不够。进程崩溃会丢失内存任务，队列也可能满。需要明确持久化交接点、失败策略和重放能力。异步化减少请求对结算耗时的等待，但不自动减少数据库总工作量，也不能消除在事件持久化之前发生故障的窗口。

**源码阅读**

- new-api：`service/billing_session.go`、`service/funding_source.go`、`model/utils.go`。
- sub2api：`backend/internal/repository/usage_billing_repo.go`、`service/gateway_usage_billing.go`。

阅读任务：区分请求内状态、进程内批量累计、持久化结算去重和账户流水。

## 13 Redis 故障时网关应该放行还是拒绝

**参考答案**

不能统一决定，要看 Redis 保存的数据承担什么职责。模型目录等允许短期陈旧的数据，可以用有效本地快照；严格权限、硬额度或必要的并发控制，则需要权威降级路径或拒绝策略。

若允许少量欠费，可以定义有限的降级窗口、并发上限和信用风险，而不能无限 fail-open。回退数据库也需要限流和熔断，避免缓存故障把全部压力转移到数据库。

对于 Redis 中的预留、锁或实时计数，还必须说明它是否是权威状态、如何持久化和如何恢复。Redis 原子操作只保证其自身操作边界，并不会让 Redis 和数据库自动成为一个事务。

**追问：Redis 扣减成功，数据库写入失败怎么办？**

必须先明确谁是权威。如果数据库是账本，Redis 通常应由已提交事件更新或能够从账本重建；如果 Redis 接受实时预留，则需要可靠记录和后续对账机制。不能随意用旧数据库余额覆盖 Redis，也不能仅靠重试一个没有幂等标识的扣减来恢复。

- new-api：`model/quota_reserve.go`、`model/utils.go`。
- sub2api：`backend/internal/repository/billing_inflight_cache.go`、`billing_cache.go`。

## 14 如何定位首 token 延迟突然升高

**参考答案**

先统一指标定义：收到响应头、收到首个 SSE 事件与收到首个有效输出内容不是同一个时间点。对工具调用、推理事件等也需要约定哪些计入首个有效输出。

把链路拆成鉴权与准入、排队、路由、连接获取、DNS/TCP/TLS、上游等待、协议处理和下游写出。按供应商、模型、账号、区域、流式模式及重试次数查看分位数，避免总体平均值掩盖局部问题。

如果上游首内容正常、客户端却很晚收到，应检查代理缓冲、压缩、Flush 和慢客户端。如果连接获取变慢，应检查连接池与并发。如果用户总延迟升高而单次成功尝试正常，应检查此前失败尝试和退避时间。

**追问：排查问题能否记录完整请求体和凭证？**

不能把完整记录作为默认做法。请求可能包含个人数据、业务秘密和工具参数；凭证不应进入日志。应默认记录必要元数据，对内容采样与脱敏，限制访问和保留期。请求关联标识和上游尝试标识通常比无差别打印原文更有诊断价值。

**源码阅读**

- new-api：`logger/`、`pkg/perf_metrics/`。
- sub2api：`backend/internal/handler/ops_error_logger.go` 与运营指标相关代码。
- 9router：`open-sse/utils/requestLogger.js`、请求明细相关实现。

阅读任务：检查当前记录的时间到底覆盖了哪一段等待。

## 15 如何设计支持大量长连接的 AI 网关

**参考答案**

先确定目标，而不是先选机器：目标请求率、平均及长尾持续时间、响应大小、可接受错误率、首内容延迟、上游配额和租户分布。根据这些数据估算在途连接、带宽、内存和存储压力。

请求执行实例可以横向扩容，但需要明确本地状态的范围。配置使用版本化快照，跨实例容量由共享协调机制或显式分配管理；当前活动流仍属于接收它的实例，通常不能在进程故障后无缝迁移。

热路径保持必要的鉴权、准入、路由和转发，避免每个 chunk 访问数据库。可异步处理的用量、统计与结算通过可靠事件交接。队列设置容量与背压，数据库通过批量写入、合适索引及热点治理提高持续处理能力。

发布时先停止接收新请求，再让已有请求在期限内完成，最后取消剩余请求并处理未完成状态。压测需覆盖慢上游、慢客户端、断连、429、依赖故障和实例退出，而不只是正常短请求。

**追问：核数翻倍能否让容量翻倍？**

只有主要瓶颈是可并行的 CPU 工作，并且其他资源还有余量时，才可能接近线性提升。若瓶颈是同一账户的行锁、数据库连接池、带宽或上游容量，更多核数可能没有收益。还要区别连接容量、每秒请求数和每秒转发字节数，不能用一个“并发数”代替所有指标。

**源码阅读**

对照三个工程的配置加载、HTTP 客户端、后台队列、缓存和退出流程，标记哪些状态只存在于单进程。

## 面试回答的组织方式

面对设计题，可以按下面的顺序回答：

1. 说明目标与约束，例如允许的延迟、陈旧窗口和失败风险。
2. 描述正常流程及每类状态的归属。
3. 解释关键机制，避免只报技术组件名称。
4. 覆盖重复、并发、超时、崩溃和依赖故障。
5. 给出取舍及验证方法，不宣称所有条件下都成立。

例如回答异步结算时，不止说“加消息队列”，还要说明事件何时可靠保存、如何去重、数据库事务覆盖哪些变动、积压如何限制，以及无法补回的故障窗口。
