# 第 23 章：多数据面部署与运行信息上报

本章给出一条保持部署简单的目标设计：一个仓库、一套程序，通过运行角色区分控制面与数据面。它不是三个参考项目已经实现的部署保证，也不要求引入 sidecar。

## 23.1 先按角色拆分

```text
管理后台 → 控制面实例
                │
           数据库与 Redis
                │
推理入口 → 数据面 A、B、C → 供应商
```

控制面负责管理配置、管理类后台任务和状态汇总。数据面负责鉴权、准入、路由、协议处理与响应交付。计价保持进程内计算，账务保持统一权威；结算 worker 初期可以运行在控制面进程。

单控制面降低管理写入与任务编排复杂度，但不具备管理面高可用。控制面故障时数据面能继续多久，取决于配置租约、凭证有效期以及准入和结算依赖，不能只因本地有配置就承诺无限服务。

配置量小时，可以定期检查版本并刷新完整快照，Redis 通知用于加速，轮询负责漏通知兜底。后续再引入第 20 章的增量协议，不必从第一版就维护复杂发布系统。

## 23.2 配置状态与运行状态分开

| 状态 | 所有者 | 例子 |
| --- | --- | --- |
| 管理配置 | 控制面 | 启用、权重、模型映射、售价 |
| 节点观察 | 数据面 | 本地连接失败、冷却、活动请求 |
| 共享资源状态 | 统一协调机制 | 账号共享配额或容量 |
| 展示状态 | 控制面汇总 | 部分区域异常、未同步节点 |

A 节点连接上游失败，可能是局部网络问题，不应直接把全局渠道配置改为停用。先本地冷却并报告事实，再按明确规则决定是否全局熔断。

即使只有一个控制面进程，也可能有多个管理员同时编辑。修改时携带读取时的配置版本，条件更新失败后提示重新加载，防止旧表单覆盖新配置。

后台应分别显示期望状态与实际状态。例如渠道期望停用、配置版本 109；A 和 B 已应用，C 最后版本为 108 且心跳过期。未知不等于健康，数据库提交成功也不等于所有节点生效。

## 23.3 Sidecar 的适用边界

Sidecar 是与主进程共同部署的辅助进程。配置 Agent 可以负责订阅、补增量、校验和本地快照交接，但不必进入每次请求的热路径。Agent 收到事件后，还需要网关确认真正应用。

出口 sidecar 可以持有上游密钥并注入认证，代价是所有上游请求多经过一个转发组件。它需要处理 SSE 背压、取消和超时，也必须独立验证调用授权，不能允许主进程任意指定地址和账号。

同一 Pod 或宿主机中的不同进程不构成强隔离保证。即使无法读取密钥，能无限借代理消费仍然有风险。只有跨项目复用、独立升级或凭证隔离需求明确时，再增加 sidecar。

不要让每个 sidecar 各自维护同一用户的权威余额，也不要把纯计算的计价引擎默认变成本地 RPC。第一版使用清晰的进程内模块通常更直接。

## 23.4 运行监控与费用分两条链路

```text
数据面 → 周期心跳 → Redis → 控制面状态页
数据面 → 可靠用量事件 → 结算 worker → 数据库账本与统计
```

监控允许短暂陈旧和少量丢失；计费事实要求可靠交接、幂等和对账。它们可以复用网络连接，但不能共用相同的丢弃与重试语义。

节点启动时建立稳定 node_id 和本次启动 instance_id，加载配置和依赖后才报告就绪。心跳记录身份、区域、程序版本、已应用配置版本、活动请求、排队、资源占用及待结算积压，并设置 TTL。

按节点存最新状态适合初期后台展示。历史 QPS、延迟分布和错误率适合时间序列系统，不宜把所有请求明细不断塞入一个 Redis JSON。节点重启后，旧实例状态需要过期，汇总时避免重复计数。

## 23.5 从请求到结算

请求开始记录 request_id、账户、Key ID、节点、模型、价格快照和开始时间。每次上游尝试另有 attempt_id、渠道、账号及实际模型。不要上报原始凭证。

SSE 期间本地累计状态与可观察用量，不需要每个 chunk 上报费用。估算和最终 usage 不能重复相加。请求结束时记录完成、失败或取消，以及用量来源和完整性；失败并不自动等于零费用。

用量事件包含稳定 event_id、请求和账户标识、价格版本、用量、来源、完整性及终态。第一版可将事件写入数据库结算任务表，持久化成功才视为交接完成；后续可替换为有明确持久化保证的队列。

调用上报接口成功，应意味着接收端已可靠保存，而不是仅进入内存队列。响应丢失时以相同事件标识重试；发送方在确认前也要有重试及存活策略。

结算端校验版本和用量，在一致性边界内完成幂等记录、账户变动、流水及完成状态。相同标识但不同内容属于冲突，不能悄悄忽略。已有预扣时结算差额，不再扣一次全额。

## 23.6 展示和故障恢复

请求可以处于“执行完成、用量确认、结算待处理”，不能因为没有账单就显示免费。正式余额和流水读取权威账务，在线节点读取心跳，性能趋势读取指标，三者不要互相替代。

| 故障 | 处理 |
| --- | --- |
| 心跳丢失 | 标为未知，后续心跳恢复 |
| 事件重复 | 幂等结算 |
| 数据库失败 | 保留事件并重试 |
| 扣款提交后确认丢失 | 重放识别已完成 |
| 结算积压 | 告警，并按风险约束新请求 |
| 事件持久化前节点崩溃 | 根据请求记录、上游查询或对账补偿 |

最后一种窗口不能靠异步化自动修复。是否保存开始记录或中间检查点，要根据损失容忍度和开销选择。普通统计队列不能作为唯一账务依据。

订阅重置、任务轮询和结算重试要明确由哪个角色启动。增加副本后，需要任务认领、租约与幂等，不能让每个 HTTP 实例重复执行全部后台工作。
