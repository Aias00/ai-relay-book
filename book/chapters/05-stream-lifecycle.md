# 第 5 章：SSE 输出开始以后，错误处理就变了

流式响应的价值是让用户尽早看到内容，但它也提前提交了 HTTP 响应。一旦响应头和部分正文已发出，中转站不能再像普通 JSON 接口一样把状态码换成 500 并返回完整错误对象。

## 5.1 五个时刻分别记录

至少区分请求到达、获得准入、收到上游响应头、收到第一段有业务意义的内容、观察到协议终态。SSE 心跳或等待提示可能早于模型内容，不能用它们计算“模型首 Token 延迟”。HTTP 首字节、内容首字节和总时长应使用不同指标。

在 new-api 兼容处理器中，`DoResponse` 先处理输出，之后再调用消费结算。在 sub2api handler 中，等待并发槽位时可能已经需要使用 streaming-aware 错误处理。在 9router 中，转换流与断开控制器负责在 HTTP 已提交后构造格式对应的终止错误。[N][S][R](91-sources.md)

## 5.2 一个网络块不是一个事件

读取操作可能只返回半个 UTF-8 字符，也可能一次包含多条 SSE 事件。解析器应保留未完成行和事件缓冲，按协议边界交付内容。工具参数、usage 和结束信息又是事件之上的业务语义，不能把网络 chunk 数量当成 Token 数量。

跨格式转发时尤其要验证结束标记。9router 的 `streamingHandler.js` 区分 Responses passthrough 与其他客户端格式，选择对应的流中错误表示。它还会检查上游 Content-Type，避免将 HTML 错误页直接当成 SSE 转换。

## 5.3 取消有三个层次

客户端停止读取、本地 AbortController 或 context 被取消、供应商确认停止执行，是三个不同事实。9router 的流控制器把断开传播到上游 signal；Go 网关也通过 context 和传输处理传播取消。传播路径存在，不意味着供应商立即停止计费。

如果请求涉及工具副作用，取消连接更不意味着撤销已经发生的操作。对账记录应保存最后已知用量、结束原因、上游请求标识和证据来源。没有最终 usage 时，不能仅因客户端关掉页面就退成零费用。

## 5.4 背压是费用问题，也是内存问题

客户端每秒只能接收少量数据，上游却快速生成，中间缓冲会扩大。生产实现需要约束缓冲字节、写入等待、空闲时间和总时长；达到限制后终止本地交付，并保留不完整状态。不能为了维持连接而无限缓存。

第 12 章的分段预算检查也处在这条数据路径上。只在接近预算时申请追加，让普通 chunk 留在本地处理；等待追加期间，必须限制读取与缓冲，不可让一个尚未获得预算的请求继续无限积累输出。
