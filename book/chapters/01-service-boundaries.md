# 第 1 章：AI 中转站到底管理什么

设想一个团队把多个编程工具、问答应用和图片任务接到同一入口。应用只知道一个模型别名，中转站却要决定使用哪个供应商、哪组凭据、哪种协议，以及这次请求由谁付费。中转站连接的不是两个 URL，而是几个彼此独立的责任系统。

## 1.1 四个面不能混成一层

数据面处理请求体、网络连接、协议转换和流式输出；调度面决定候选模型、账户、冷却与并发；计费面把用量转换为费用并维护预算；管理面让运营者修改这些规则。管理界面里的配置只有进入运行时快照，才会实际影响某次请求。

例如管理员把某模型输出单价从 8 改为 12。如果已经运行的请求结束时读取最新价格，用户看到的单价就可能与准入时不同。这个问题不由界面解决，而由请求级定价版本解决。管理数据与请求事实的生效时刻必须明确。

## 1.2 三个工程的切入点

| 工程 | 本书观察到的主要组织方式 | 优先阅读的问题 |
| --- | --- | --- |
| new-api | Go 网关、供应商 adaptor、用户与分组、钱包/订阅、表达式定价 | 如何把不同上游用量转换为收费 |
| sub2api | Go 服务、分组与账户调度、并发槽位、在途预留、事务后扣 | 多个账户和异步计费如何衔接 |
| 9router | Next.js 入口、open-sse 转换引擎、provider connection、combo、本地统计 | 怎样让不同客户端格式连接不同供应商 |

这不是功能排名。三个项目都覆盖多个面，但主链路的抽象不同。9router 的成本统计不能直接当成 new-api 的用户钱包；sub2api 的订阅对象也不应仅凭同名字段就映射到 new-api 的订阅周期。

## 1.3 用户、Key、渠道和账户

用户是被计费或被分配资源的主体。API Key 是调用入口，可以拥有自己的限额。渠道描述连接到上游的配置，账户则是具体供应商身份或额度来源。一个用户可以有多把 Key，一个渠道或账户池可以服务多个用户。

用户余额减少与 Key 剩余额度减少，通常是同一笔消费在资金和访问限制两个维度的反映，不是重复收两次钱。另一方面，上游实际成本与向用户收取的价格可以不同，必须分字段记录；否则利润分析会把售价当作采购成本。

## 1.4 一条请求至少有三种身份

业务请求 ID 用来关联客户端操作；上游尝试 ID 用来区分切换账户后的每一次发送；结算 ID 用来决定同一项费用是否已经处理。必要时另设预留 ID，并显式保存关联关系。不要把一个客户端可重复传入的字符串当作所有层级的身份。

如果客户端请求 A 在账户 X 超时后转向 Y，最终日志应能表达 A 有两次尝试，其中 X 的用量未知，Y 返回了已知用量。仅保留“最后使用 Y，成功”会丢失后续账单核对的依据。
