# 第 9 章：sub2api 的在途预留与事务后扣

sub2api 把“现在允许再发多少请求”和“已经确认消费多少”分开。普通钱包在途预留先登记占用，不立即扣掉钱包余额；响应后的用量任务计算实际费用并提交数据库扣款。这比真实预扣更容易释放未执行占用，但仍需处理异步任务丢失和缓存失效。

## 9.1 Redis 保存请求明细

固定版本 [S](91-sources.md) 使用两类钱包 key：

```text
billing:inflight:{用户ID}      ZSET：预留 UUID → 到期毫秒
billing:inflight_amt:{用户ID}  HASH：预留 UUID → 美元金额
```

同一用户 A、B 两笔请求可以分别占用 0.02 和 0.05 美元，而用户余额本身尚未因此减少。预留 ID 在服务内通过 UUID 生成；它不是天然等于客户端请求 ID 或最终数据库计费去重 ID。

Lua 会清理过期成员，遍历 HASH 金额求和，再判断准入并登记占用。它避免多进程分别看到同一份可用余额后全部放行，但每次遍历的工作量随在途数量增加。若用户并发规模很大，应评估维护预留总额的方案及其清理一致性。

## 9.2 首笔请求与异常路径有特殊政策

普通估算预留只在已有在途请求时检查“余额减在途合计是否覆盖新估算”。没有其他在途请求时，依赖外层基础余额检查，不在 Lua 中要求余额覆盖整笔估算。Redis 操作失败、缓存能力缺失等情况下，普通预留路径可以 fail-open。

因此它是一项减少并发透支的措施，不是严格保证每次最大费用都有资金覆盖。固定金额收费路径另有足额检查，不能把这两种准入政策合并描述。

Token 估算大致使用请求体字节数除以 4 作为输入估算，加客户端输出上限；缺省输出按配置取值，默认 8192，并受配置上限约束。它比精确 tokenizer 便宜，但不是模型真实 Token 数。费率、路由映射与倍率也参与估算。

## 9.3 预留比 handler 活得更久

默认 TTL 为 900 秒。普通钱包长请求可每 TTL/3 续期；handler 结束后停止续期。异步计费任务通过 `Acquire` 增加引用，任务结束后归还，handler 与计费引用都释放时才删除预留。这样可以覆盖“客户端已收到答案，后台尚未扣费”的窗口。

如果进程崩溃，Redis 预留最终会过期，但到期只释放占用，不会自动产生结算任务。Redis 中记录了估算金额，也不足以推导最终输入、输出与采购成本。

## 9.4 订阅和 Key 的 scope 预留

对请求前可确定金额的收费，`ReserveFixedCharge` 还可登记 `sub:订阅ID` 和 `apikey:KeyID` scope，在 Redis 保存请求金额，并结合数据库权威用量检查额度。这些 scope 不续期。普通 `ReserveInflight` 会跳过订阅计费，因此不是所有订阅请求都有这类预留。

这与 new-api 的订阅预扣表不同：一个是 Redis 临时占用，一个是已增加订阅用量后的数据库请求记录。

## 9.5 最终扣费有事务去重

`usageBillingRepository.Apply` 先在事务内认领 `usage_billing_dedup` 的 `(request_id, api_key_id)`，核对请求指纹，再更新适用的钱包、订阅和额度，最后提交。重复记录不会再次扣费，内容冲突也不是静默视作成功。

但是调用它的普通 usage worker 仍是进程内执行器。尚未执行或尚未可靠保存的任务可能随崩溃丢失。数据库幂等解决“同一任务执行两次”，没有解决“任务根本没有执行”。特定批量图片路径有独立 hold 和恢复实现，本章结论不覆盖这些路径。

**练习：** 分别在“预留完成”“任务入内存队列”“数据库提交”“Redis 释放”后让进程退出。哪一步可以靠最终扣费去重安全重试，哪一步还缺持久化任务？
