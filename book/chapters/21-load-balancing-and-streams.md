# 第 21 章：四层七层负载与多节点长连接

四层负载主要按连接信息分流，七层负载理解 HTTP 并按请求选择后端。两者都能承载 SSE；都不会把同一条响应流的不同事件随意分发给不同执行节点。

## 21.1 两种负载的边界

| 维度 | 四层 | 七层 |
| --- | --- | --- |
| 信息 | IP、端口、协议、连接 | 域名、路径、请求头、Cookie |
| 分配单位 | TCP 连接；UDP 通常按流 | HTTP 请求 |
| TLS 常见方式 | 透传，后端终止 | 入口终止，可再加密到后端 |
| HTTP 路由 | 通常不解析路径 | 可按管理与推理接口分流 |
| 开销 | 协议处理通常较少 | 解析及策略更多，实际取决于实现 |

四层可以由 NAT、直接路由或 TCP 代理实现，不能把某一种转发路径推广到所有实现。七层 TLS 终止后仍可通过 TLS 或 mTLS 连接后端，内部不必明文。入口能看到认证头，因此也属于凭证信任边界。

一条 HTTP/2 连接可承载多个并发请求。四层通常把它们交给同一后端；七层代理支持相应协议和调度时，可以把不同请求发到不同节点。于是最少连接不一定等于最少活跃请求。

## 21.2 单流固定节点

```text
请求 R1 → 入口 → 节点 A → 上游
请求 R2 → 入口 → 节点 B → 上游
```

R1 的客户端响应、上游连接、解析状态、价格快照、用量累计和取消控制由 A 管理，不需要每个包同步 Redis。下一次请求可以去 B，所以普通 SSE 不要求同一用户永久黏在一个节点。

确有会话亲和性时，应明确绑定的是上游账号、模型会话还是数据面实例。应用会话可以通过共享状态保持，不等于必须绑定 TCP 连接。

## 21.3 连接容量与 Go 调度

一万个流式连接不要求一万个系统线程。Go 可以复用线程调度大量等待网络的 goroutine，但每条流仍占用内存、文件描述符、TLS 状态、socket 和应用缓冲，还可能对应一条上游连接。

稳定状态下，平均在途数量约为到达率乘以平均停留时间。假设每秒 100 次请求、平均 30 秒，平均在途约 3000；这不是容量上限，还需考虑突发、长尾和重试。

增加 CPU 核数主要缓解可并行计算。如果瓶颈是数据库热点、连接池、带宽或上游限流，并发更高可能只是让等待更多。压测应分别报告请求率、活跃请求、转发字节量和延迟。

## 21.4 SSE 代理配置

| 项目 | 风险与处理 |
| --- | --- |
| 响应缓冲 | 积攒后发送，需关闭或按流调整 |
| 空闲超时 | 无内容间隔过长被断开，按业务设置 |
| 总时限 | 长生成被固定时限截断，需要产品约定 |
| 压缩 | 小块内容可能未及时刷新，需要实际验证 |
| 自动重试 | 可能重复生成，按执行阶段及幂等性限制 |
| 慢客户端 | 无界缓存引发内存增长，采用有界缓冲与取消 |

连接、首内容、流空闲、总截止时间是不同超时。TCP 保活也不是 SSE 心跳，应用心跳应由理解协议的组件生成。已输出部分内容时，不能默认切换上游并拼接第二次生成。

## 21.5 扩缩容与退出

新节点先同步配置并准备好依赖，再进入就绪状态接收新请求。缩容先从调度中摘除，停止接收新请求，再等待活动流结束；到达期限后取消剩余流并可靠处理必要记录。

负载均衡排空、应用退出期限和部署系统终止期限需要配合，否则应用仍在等待，外部已强制杀进程。新配置只影响之后开始的请求，在途请求保留原价格版本。

## 21.6 故障恢复不等于连接迁移

节点 A 崩溃时，B 不能仅凭同一配置接管它的 TCP/TLS 连接，也未必知道客户端最后收到了什么。普通 SSE 通常中断，由客户端按约定重试；重试生成不保证相同内容，也可能再次产生费用。

如果需要重连后继续交付原结果，可把生成任务与交付连接分离：后台生成持续写有序事件，SSE 节点订阅，客户端重连携带最后收到的事件 ID，任意节点补发后继续订阅。仅设置 Last-Event-ID 而没有可重放事件存储并不能实现恢复。

事件保留、访问授权、序号、生成任务存活与消息重复都要有规则。这是一项独立能力，不应作为普通中转的默认复杂度。

## 21.7 异步化的边界

把统计与结算移出转发关键路径可以缩短等待，但数据库总工作量仍存在。持续写入大于消费能力时，队列会积压；需要批量写、合理索引、热点治理和背压。

旁路采集适合指标与分析。若用量是唯一扣款依据，需要明确可靠交接点、幂等和对账。启动 goroutine 或增加核数既不能提供持久性，也不能消除重复扣款与漏账窗口。
